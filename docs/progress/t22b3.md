## 1. Drag never selects (owner decision on Finding A: option 2+3 combined, per the brief)

**Mechanism.** `@react-three/fiber`'s own `events.d.ts` (`IntersectionEvent<TSourceEvent>`):
```ts
/** Delta between first click and this event */
delta: number;
```
quoted and confirmed against the implementation (`events-e51d7528.esm.js`): `const delta = isClickEvent ? calculateDistance(event) : 0`,
where `calculateDistance` is `Math.round(Math.sqrt(dx*dx+dy*dy))` against `internal.initialClick` — R3F's own canvas-level
`pointerdown` listener records this on **every** pointerdown reaching the canvas, regardless of what (if anything) was hit, so it
correctly reflects the true drag distance even for a drag that starts on an actor (a non-R3F object).

**Fix**, one call site: `src/scene/bay/Bay.tsx`'s group `onClick` now reads
```ts
if (isR3fClickDrag(e.delta)) return;
```
before calling `onSelect`, where `isR3fClickDrag` (new, `src/scene/interaction/pick.ts`) is `delta > DRAG_PX` (the same `DRAG_PX = 4`
threshold `isDrag` already uses at the canvas level). `stopPropagation()` stays unconditional (unchanged). Bays, belts and staging
share this one handler (confirmed: `grep -rn onClick src/scene` has exactly one hit outside dev/preview chrome), so this single change
covers all three, plus the actor-starts-a-drag-that-falls-through case Finding A reported (the Bay handler now rejects it on `e.delta`
regardless of how the click reached it). Camera glyphs and actors keep the existing canvas-level `isDrag` check, unchanged, per the
brief ("keeping the existing canvas-level rule for actors").

**Unit test** (`src/scene/interaction/pick.test.ts`, `isR3fClickDrag`): `delta=4` → click, `delta=5` → drag, `delta=0` → click —
same boundary as `isDrag`'s own existing test. A full R3F-rendered test of `Bay.tsx`'s `onClick` was not attempted: this project has
no `@react-three/test-renderer` (grepped `package.json`/`node_modules` for it, no hits), so there is no practical way to render a Bay
and dispatch a real pointer-down/move/up sequence through R3F's own event pipeline in a unit test; the pure-logic boundary is what
`pick.test.ts` already tests this way for `isDrag`, so the new test follows the same, only practical pattern.

**docs/04-scene-spec.md** section 1: "as before" replaced with the actual rule (drag never selects, anywhere, two independent
distance checks sharing one threshold).

**e2e.** `e2e/t22b-scene.spec.ts`'s "a camera drag that starts on an actor is not a click" (written in 22B.1, already asserted
`selection === null` for the 40 px actor-drag case) needed no assertion change — it was already encoding the target behaviour; the

involved) was **not** added as a new e2e test: there is no probe exposing a bare-floor screen point (only `__pickProbe.points()`,

## 2. Toast placement (owner decision, docs/06 §7.10)

**Rule:** a live-event toast (`notifyRuntime.tsx`'s `toast.custom()`) sits `top-center`, offset `{ top: SCENE_SAFE_AREA.top + 16 }`
= 136 px (the 120 px the 3D view already keeps clear for the KPI row, plus the KPI chips' own 16 px margin). Every other toast
(`/events`, `/reports`, …) keeps sonner's own `bottom-right` default. Verified by viewport math (toast width is a `sonner`
constant, `TOAST_WIDTH = 356` px, confirmed by reading `node_modules/sonner`): centred horizontally, the toast's x-range never
reaches the 360 px right column (inspector/tray) at either 1920×1080 or 1366×768, and sits entirely below the KPI-row/map-controls
band vertically — confirmed by eye in every captured screenshot too (§ below).

### A real bug found and fixed mid-session (reported in full, not glossed over)

**First implementation** (wrong): `src/app/AppShell.tsx` rendered one of two `<Toaster>` elements, switched on
`useLocation().pathname === '/live'` — `position="top-center"` on `/live`, sonner's default otherwise. `pnpm typecheck/lint/test`
all passed, and the specific toast screenshots looked right, but a regression run of `e2e/t22a-events.spec.ts` found "Open" on a
toast — clicking a live-event toast's "Open" button while still on `/live`, which navigates to `/events/:id` — now reliably
failing (repeated 2/2 times) where it had been T22.11's own confirmed-fixed, reliably-passing case.

**Root cause** (read from `node_modules/sonner/dist/index.mjs`): sonner groups toasts by **position** into separately-keyed
`<ol>` lists (`key: position`); a toast with no explicit `position` of its own renders into the group matching the **Toaster's
own** `position` prop at render time. Clicking "Open" calls `navigate(...)`, which (since `useTransitions={false}`, task 22.11)
commits synchronously; `AppShell`'s `useLocation()` then reads the new pathname in the **same** update, flips `isLive` to `false`,
and the Toaster's `position` prop changes from `'top-center'` to the default — which sonner reads as "render a different `<ol>`
with a different key," unmounting the old one (and the toast's own DOM node inside it, including the very button that was just
clicked) and mounting a new one. The click's own event handling raced this remount.

**Fix:** one `<Toaster offset={{ top: 136 }}>` stays mounted everywhere (never swapped); the `top-center` position is set **once,
per toast, at creation**, as an option on `notifyRuntime.tsx`'s own `toast.custom(..., { position: 'top-center' })` call — not read
reactively from the current route. The top offset only affects top-positioned toasts (bottom-right toasts read the bottom/right
offsets instead, untouched), so this has no effect on any other toast anywhere else. `docs/06` §7.10 rewritten to describe the
corrected mechanism and name the bug explicitly, so a future reader does not reintroduce it.

**Confirmed fixed:** before the fix, "Open on a toast" failed 2/2 attempts at the exact same step (`toHaveURL` never resolving,
120 s+). After the fix, repeated runs show a materially different, improved failure signature — one run got all the way past both
the click and the URL change, failing only on a 5 s-default wait for the destination drawer; see §6 for the honest remaining
picture (this sandbox's pre-existing, already-documented `startPeak()`/CPU-contention flakiness, not this bug, explains what is
still inconsistent).

## 5. Nav timeline split — answers 22.11's open question directly

`e2e/t21-nav-leak.spec.ts` extended: `leave()` now also returns `dispatchDelayMs` (Node `Date.now()` just before the call vs. the
page's own `Date.now()` at the very start of the evaluated script — the closest honest proxy for "input delay" this harness has;
see the code comment for why a literal click-timestamp delay does not exist here: navigation is a synthetic `pushState` +
dispatched `popstate`, not a real hardware click). The longtask accumulator now keeps every entry's `{start, duration}`
(`window.__t21LongTasks`), reset each cycle; each cycle classifies them against `pushedAt`: `before` (`start < pushedAt`, with
`preClickOverlapMs` = how much of that task's duration still runs *past* the push) and `atOrAfter` (`start ≥ pushedAt`, summed as
`postClickMs`).

### SwiftShader, default mode, 10 cycles (also item 6's required run)
Leave times (ms): 41026, 24705, 17756, 28464, 26581, 13676, 35534, 19092, 20303, 19957 (min 13676 / median 20130 / max 41026).
Every cycle but one had exactly 2 longtasks, both classified "before" the push, with `preClickOverlapMs` ≈ the entire leave time
(e.g. cycle 2: one task overlaps the push by 24705 ms — almost the whole 24705 ms leave). **Read naively, this says "nearly all of
the leave time is pre-existing work that started before the click" — the brief's first bucket.** A follow-up diagnostic (same
mechanism, instrumented to also print each before-task's **lead time**, `pushedAt − start`) shows this reading is wrong: the lead
is **0.2–0.7 ms** in every case (4 extra cycles checked), i.e. the task began a fraction of a millisecond before the in-page
`performance.now()` capture — a measurement-boundary artifact of capturing `t0` one or two statements into the same synchronous
script, not a separate task that was genuinely already running. The same task's `duration` then extends **13,676–74,094 ms past**
that instant.

**Answer: on this sandbox, under SwiftShader, essentially 100% of the leave time is the one synchronous unmount/remount commit
triggered immediately by the push itself — not input delay behind separate pre-existing background work (no warmup/shader-compile
task was found running a meaningful interval ahead of the click), and not meaningfully "teardown starting after the click" either
in the sense of a second, later task — it is one task, starting essentially at the click, that *is* the teardown.** This directly
confirms (not just infers from coincident timestamps, as `docs/progress/t22b2.md` Finding E did) that the destination-visible/
canvas-gone/long-task-end are one real, synchronous cost, matching `docs/progress/t22-11.md`'s own open question with hard evidence
instead of circumstantial timing.

### Real GPU, same launch flags as the fps gate (ad-hoc script, same instrumentation; no heap/leak gate — `t21-nav-leak.spec.ts`
### itself already re-ran separately, default mode, see §6)
3 cycles: canvasGone 29, 50, 62 ms. A follow-up 4-cycle lead-time check: cycle 1 one longtask, lead 0.50 ms, duration 52.0 ms
(ends 51.5 ms past the push); cycles 2–4 had **no** longtask at all (the whole leave — well under 50 ms — never crossed the
browser's own ~50 ms longtask threshold). **Same pattern as SwiftShader, at a vastly smaller absolute scale**: confirms
`docs/progress/t22-10.md` §8's own speculation ("on a real GPU the render loop's own long-task time would very likely be much
smaller") directly, for the first time with real-GPU numbers. `dispatchDelayMs` on the real GPU: 10–24 ms, every cycle — genuinely
small, unlike SwiftShader's cycle-1 outlier (5343 ms, a one-off warm-up cost, cycles 2–10 otherwise 9–168 ms).

**Teardown on the real GPU: 29–62 ms — far under the brief's 500 ms stop condition.** Not triggered; nothing to stop and report.

around y=162, both past 136, so the toast's top edge overlapped the bottom of the "Belts loaded" / "Today" sub-lines.

**Fix.** The KPI row now reports its own measured bottom edge instead of the offset being a second fixed guess:
- `src/features/live/KpiChips.tsx`: the chip row's outer `div` (`data-testid="kpi-chips"`) takes a ref; a `ResizeObserver` on it calls
  `uiStore.getState().setKpiRowBottom(el.getBoundingClientRect().bottom)` on mount and every resize (collapse/expand, chip count
  changing at the 1700/2000 px breakpoints, viewport resize), and `setKpiRowBottom(null)` on unmount (leaving `/live`).
- `src/stores/uiStore.ts`: new `kpiRowBottom: number | null` field and `setKpiRowBottom` action (not persisted — a transient layout
  measurement, not a preference). `src/stores/hooks.ts` exports `useKpiRowBottom()`.
- `src/app/shell/toastOffset.ts` (new, pure, unit-tested): `computeToastOffsetTop(kpiRowBottom)` returns `kpiRowBottom + 12` when
  measured, else `TOAST_OFFSET_TOP_FALLBACK` (`SCENE_SAFE_AREA.top + 16` = 136, the old 22B.3 guess) when the KPI row is not mounted
  (every page but `/live`) — moot there since every other toast already uses sonner's bottom-right default, untouched.
- `src/app/AppShell.tsx`: reads `useKpiRowBottom()`, computes `{ top: computeToastOffsetTop(kpiRowBottom) }` with `useMemo`, and
  passes it to the Toaster's `offset` prop every render. **Only the offset *value* changes; the `Toaster`'s own `position` prop is
  never swapped** (unchanged from the 22B.3 fix) — the 22B.3 bug class (sonner regrouping toasts into a different `<ol>` on a prop
  change, tearing down a toast mid-click) cannot recur from this change, confirmed by rereading `node_modules/sonner`: `offset`
  is read into CSS custom properties on every render, not used as any part of a group key.
- `docs/06-visual-language.md` §7.10 rewritten to describe the measured offset and name the corrected mechanism.

**Unit test** (`src/app/shell/toastOffset.test.ts`): `computeToastOffsetTop(null)` → the fallback (136); `computeToastOffsetTop(157)` →
169 (1920x1080's architect-reported figure + 12); `computeToastOffsetTop(162)` → 174 (1366x768's).
