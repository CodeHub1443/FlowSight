### Finding A — a drag starting on an actor still selects the bay underneath it (needs an owner decision)

**Evidence.** `e2e/t22b-scene.spec.ts`'s "a camera drag that starts on an actor is not a click" test: a mouse-down on
a person, a 40×10 px move, mouse-up. Expected `selection === null`; observed `selection === {kind:'bay', id:'B02'}`.
Reproduced twice, including once on an otherwise-quiet machine (not environment noise).

- `src/scene/interaction/ActorInteraction.tsx:174-188` (`onClick`): `if (isDrag(start.x, start.y, e.clientX,
  e.clientY)) return;` — this `return` happens **before** `e.stopPropagation()` is ever called (that line only runs
  a few lines further down, in the `decision.type === 'select'` branch). So for a drag, the native DOM `click` event
  is never stopped and continues to bubble from the canvas up to R3F's own listener on the Canvas wrapper `<div>`.
- `src/scene/bay/Bay.tsx:148` — the Bay's `<group onClick={(e) => { e.stopPropagation(); onSelect(...) }}>` has **no
  drag/distance guard of its own**; it selects on any click that reaches it, full stop.
- R3F's own click-vs-drag protection (`node_modules/.../@react-three/fiber/dist/events-e51d7528.esm.js:1013`,
  `if (!isClickEvent || internal.initialHits.includes(eventObject))`) only suppresses a click on an object that was
  **not already under the pointer at `pointerdown`**. The test's drag stays inside the same bay's floor footprint
  the whole time, so the Bay `group` is in `initialHits` at mousedown **and** in `hits` at the click — R3F calls its
  `onClick` regardless of the 40 px move. R3F's guard is a "same target" check, not a distance/drag check.
- `docs/04-scene-spec.md` section 1 says: *"A click on nothing of ours, and any drag, reaches R3F and the bays as
  before (bays, belts and staging stay selectable)."* This is a precise description of the **observed** behaviour,
  and `docs/progress/t22b.md`'s own decision log (item 6 of "decisions and deviations") frames bay-selection-on-drag
  as unchanged, pre-existing behaviour, not a regression.
- The test's own assertion (`expect(selection).toBeNull()`), written in 22B.1 and never run until this session,
  **contradicts** that documented "as before" behaviour.

**This is a conflict between the written spec and the written test, not a bug with one obvious fix** — exactly the
brief's stop condition ("a defect that needs a design decision is reported with options, not decided"). Options,
not decided here:

1. **The test's assertion is wrong; docs/04 is right.** Bays have always been selectable through a small drag (this
   is not new to 22B), and the "drag over an actor" case should be treated the same way. Fix: change the test to
   expect `{kind:'bay', id:'B02'}` instead of `null`.
2. **The test is right; a drag that starts on an actor should suppress any resulting R3F click too**, not just an
   actor-hit click. Fix: in `ActorInteraction.tsx`'s `onClick`, when `isDrag(...)` is true **and** `start` was
   recorded (i.e. the drag began inside the canvas, on top of whatever was picked at `pointerdown`), also call
   `e.stopPropagation()` before returning — a small, scoped change, but a real behaviour change for any drag that
   happens to start on an actor.
3. **Broader: any drag over the canvas (not just ones starting on an actor) should suppress the resulting bay
   click**, project-wide. This would need a shared drag-distance guard that pairs with `OrbitControls` (which has no
   such guard of its own for R3F's click dispatch today) and would affect plain bay-floor drags too — well beyond
   this task's scope, and a bigger decision.

**Not fixed.** Not decided. The test's assertion was left as written (changing it to match option 1 would be
silently resolving the conflict in the spec's favour without the owner's sign-off, which the brief's stop condition
specifically rules out).

### Finding C — forcing a not-OK camera: possible, but only probabilistically, via the `system` trigger

The brief describes "using the existing mock controls to force a not-OK camera" as a given. There is **no direct
"set this camera's health" control** (`src/data/mock/core/controller.ts`'s message union has no such message type).
However, the existing `system` category button in the dev "Simulator" panel (`MockControls.tsx`, `source.trigger
('system')`) picks a **random** key within the category; 4 of its 5 non-timeline keys
(`system.camera_offline/obstructed/defocus/moved`) **do** call `depot.ts`'s real `setCamera()`
(`src/data/mock/core/depot.ts:642-655`) — only `system.pipeline_lag` doesn't. So clicking "System" repeatedly forces
a not-OK camera with roughly 80% odds per click, not deterministically on the first try: this session's own runs
needed 4 attempts once and worked on the first attempt another time. Works in practice with a short retry loop; not
a one-click deterministic control as the brief's phrasing implies.

**Finding E — the ~12-17 s belongs to (b)=(c): the single synchronous React commit itself, not to anything after it.**

1. **(b) and (c) are the exact same millisecond, every cycle, with no exceptions.** This is architectural, not
   coincidental: `[data-testid="scene-canvas"]` is the wrapper `<div>` that `LiveScene` itself renders
   (`src/app/LiveScene.tsx:246-253`), and `/trucks`'s destination content (`Placeholder`, `src/app/Placeholder.tsx`,
   not a lazy route — confirmed in `src/app/routes.tsx:43`, no `Suspense` around it) mounts in the **same** React
   commit that unmounts `LiveScene`. There is no "old canvas stays mounted after the route commits" question to
   answer here, because they are provably the same commit — this directly answers the brief's "if the old canvas
   stays mounted after the route commit, find out why" by showing that it does **not**.
2. **The long-task sums roughly match or exceed the whole leave time** (e.g. cycle 1: 8 long tasks summing to
   36322 ms against a 34279 ms leave; every other cycle's 2-3 long tasks sum to within a couple of seconds of the
   leave time). Since `useTransitions={false}` already makes this commit run outside `startTransition` (confirmed
   in `src/app/App.tsx`), **the gap is not a scheduling delay waiting for a transition to be allowed to commit** —
   it is the real, synchronous wall-clock cost of that one commit (tearing down the whole live `LiveScene`/R3F
   subtree — hundreds of Fiber nodes, cleanup effects, the WebGL canvas itself — and mounting the placeholder)
   actually executing on this machine's main thread.
3. **This is a materially different situation from `docs/progress/t22-10.md`'s own measured entry points**
   (sub-second commits to `/events`), and the difference is not the destination (both are "leave `/live`"): this
   spec runs 10 mount→unmount cycles back-to-back with only an 800 ms gap between them, so each navigation leaves
   (and the next mount re-creates) a **fully "hot," continuously-ticking** scene — `useFrame` running, 4 Hz store
   flushes in flight — right up to the moment of the push, unlike `t22-10`'s isolated single clicks from specific,
   deliberately-quiesced `settled`/`warmup` conditions. Tearing down a scene that is mid-flight, repeatedly, is
   plausibly and evidently far more expensive than committing a lightweight destination from a quiet start. This is
   reported as the best-supported explanation from the evidence gathered, not re-verified against an isolated
   single-cycle rerun of `t22-10`'s own harness (out of this session's time budget).
4. **(d), GPU release, could not be pinned to a timestamp.** Every cycle's 10 s poll window reported `n/a`: GPU
   memory (geometries/textures) never matched the start baseline within 10 s of the canvas leaving. This is most
   likely **a race with the very next cycle's own mount** (the loop waits only 800 ms after `leave()` before calling
   `go('/live')` again, which starts allocating new geometries/textures before the old renderer's
   `useReleaseOnUnmount` → `disposeAll` pass — scheduled a passive-effect tick plus one more macrotask after commit,
   per `src/scene/useReleaseOnUnmount.ts`'s own comment "disposed a task later" — has necessarily finished), so the
   polled count can pass through the exact baseline value, if it ever does, faster than a 100 ms-interval poll can
   catch it, or never pass through it at all if the new mount's allocations overtake the old mount's disposal.
   **This is not evidence that disposal fails**: the leak gate's own cycle-10 sample (above) confirms geometries and
   textures are back to the exact start values by the next checked cycle, so disposal is confirmed correct — this
   session's own (d) instrumentation just could not isolate *when*, within a single 800 ms-spaced cycle, that
   happens. A follow-up with a longer gap between cycles (so disposal and the next mount do not race) would resolve
   this cleanly; not attempted here, reported as a gap.

**Not fixed; nothing needed fixing.** No in-scope defect was found in `useReleaseOnUnmount.ts`, `gpuRelease.ts`,
`App.tsx` or `routes.tsx` — the leak gate itself passes, and the latency, while slower than ideal, is fully
explained by genuine, unavoidable synchronous commit cost under this session's ambient load, not by a code path
that keeps the old canvas alive or defers its release incorrectly.
