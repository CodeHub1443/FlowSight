# Task 22.10: navigation latency when leaving /live

Main worktree, `master`, HEAD `afeab24` (task-22.9 integration), clean tree at the start. Mode: INVESTIGATION.
Nothing in `src/` is changed by this session: `git diff -- src` is empty (the one experimental edit, part 4 below,

## 1. Summary

**Hypothesis confirmed.** Every navigation away from `/live` (bell "View all events", tray row icon, KPI "Needs
attention" rows, toast "Open") is wrapped in `React.startTransition` because `src/app/App.tsx`'s `<BrowserRouter>`
does not set `useTransitions`, and react-router 7.18.4 defaults to wrapping router state updates in a transition
unless `useTransitions={false}` is passed. On this sandbox's CPU-rendered (SwiftShader) `/live` scene, that
transition is starved for seconds: the URL changes in 0-1 ms (confirmed: `page.url()` needs no page JS, matching the
task-22.9 "Open on a toast" investigation), but the destination page's heading/drawer does not become visible for a
**median of 7-22 s** across every one of the four entry points and all three load conditions (current behaviour).
Setting `useTransitions={false}` on the one `<BrowserRouter>` drops that to a **median of 7-300 ms** — roughly
100-1000x faster — while the measured main-thread long-task time **does not change** (medians 17.3 s vs 17.6 s): the
fix does not make the scene lighter, it changes *when* the route commits relative to that busy work.

## 3. The router-transition claim, verified against the installed package

The brief's own hypothesis said react-router 7.18.4's `BrowserRouter` "has no `useTransitions` setting." That is not
quite right — it has one, and the installed package's own type declaration and implementation confirm the brief's
mechanism exactly:

`node_modules/.pnpm/react-router@7.18.4.../react-router/dist/development/dom-export.d.ts` (`BrowserRouterProps`):
```ts
/**
 * When `false`, router state updates are performed with `ReactDOM.flushSync`...
 *   `React.useOptimistic` on any navigations or state changes.
 * ...
 */
useTransitions?: boolean;
```

`dist/development/chunk-HQO5H5CC.js` (`BrowserRouter`'s actual history listener):
```js
let setState = React.useCallback(
  (newState) => {
    if (useTransitions === false) {
      setStateImpl(newState);
    } else {
      React.startTransition(() => setStateImpl(newState));
    }
  },
  [useTransitions]
);
```

`src/app/App.tsx` (unchanged, HEAD):
```tsx
<BrowserRouter>
  <AppRoutes />
</BrowserRouter>
```

No `useTransitions` prop is passed, so `useTransitions === false` is never true, so **every** router state update —
every click on the four entry points, every `popstate`, the initial `/` → `/live` redirect — runs inside
`React.startTransition`. `CHANGELOG.md` places the stabilisation of `unstable_useTransitions` as `useTransitions`
under `v7.15.0`; the installed `7.18.4` is well past that, so the prop is live, not experimental, in this project's
pinned version. No other app code calls `startTransition`/`useTransition` (`grep -rn "startTransition\|useTransition" src`:
no matches outside `node_modules`), so this one prop is the only lever.

## 4. Methodology

### Entry points (all four from task 22A, confirmed by reading the components)
| Entry point | Component | Navigate call | Destination |
|---|---|---|---|
| Bell "View all events" | `src/app/shell/AlertBell.tsx:97` | `navigate('/events')` | `/events` |
| Tray row icon ("Open in Events") | `src/features/live/Tray.tsx:111` (`Row`'s `href`) | `<Link to={eventPath(id)}>` | `/events/:id` |
| KPI "Needs attention" row | `src/features/live/kpiDetail/details.tsx:438` (`GroupRow`) | `<Link to={eventsPath({...group})}>` | `/events?group=` |
| Toast "Open" | `src/app/shell/notifyRuntime.tsx:61` | `navigate(eventPath(tt.eventId))` | `/events/:id` |

### Conditions
- **settled**: wait for `[data-testid="quality-badge"]`'s `data-state` to read `monitoring` (fps is sampled, not `-`),
  then click.
- **warmup**: remount `/live` client-side (`history.pushState` + `popstate`, no reload — the mock simulator and its
  backfilled alerts persist across it, matching `e2e/t21-nav-leak.spec.ts`'s own `go()`), then click immediately,
  with no wait. The governor's `warmupMs` is 5000 (`tierGovernor.ts`).
- **burst**: same as settled, plus the simulator speed raised via `window.__soakProbe.setSpeed()` (the same
  programmatic hook `pnpm soak` uses — no debug-panel UI, no restart).

### Two sandbox-specific adaptations (both inside the brief's "use the closest working condition" allowance)
1. **`startPeak()` landed this time** (`peakLanded=true` in both runs) — unlike the task-22.9/22.9b sessions, this
   sandbox's `startPeak()` poll succeeded within its 60 s budget both times. No fallback was needed; the harness
   still has a `try/catch` around it and logs which branch ran.
2. **The 'settled' and 'burst' conditions need `window.__qualityFpsOverride`.** First smoke run without it: the
   quality badge read `data-state="warmup"` for **172 consecutive polls over 90 s**, tier already `low` — it never
   reached `monitoring` at all. Root cause, read from `src/scene/tierGovernor.ts` `frame()`: with no override, any
   frame arriving more than `maxFrameGapMs` (800 ms) after the last one is treated as "the browser paused drawing,"
   which resets the warmup settle timer. This sandbox's real SwiftShader fps under this test's own load is near or
   under 1 fps (5-50 frames measured over a 7-25 s window), so almost every frame gap exceeds 800 ms and the governor
   can never leave warmup. `window.__qualityFpsOverride` (already used by `e2e/auto-quality.spec.ts` for the same
   reason — "a software rasteriser cannot run fast or slow on demand") skips that gap check entirely. Setting it to
   `45` for `settled`/`burst` (and `null` for `warmup`, where the real low fps is exactly the condition under test)
   let `monitoring` be reached reliably (confirmed per-rep below, `stateAtClick` column). **This does not stand in
   for a real GPU** — see section 8.
3. **Toast needs a speed floor to arrive at all.** Bell/tray/KPI read already-backfilled alerts (unaffected by
   speed). A toast needs a *new* live event, so `settled`/`warmup` hold the simulator at a minimum speed (10x/60x)
   just so one arrives inside a bounded wait — chosen so `warmup`'s wait is short enough to still be inside the 5 s
   governor window on the clicks that landed there (see `stateAtClick` below: it did, mostly). `toast`'s `burst` cell
   has 1-2 of 5 reps capped (no toast within 60 s) in each run — reported as a gap, not forced; see section 8.

### What each number means
- **url ms**: `Date.now()` from just before `locator.click()` until `page.url()` (no JS execution, same channel
  task-22.9 used to show the URL updates while the page was unresponsive) matches the destination pattern. Capped at
  15 s, not asserted.
- **heading ms**: from the same click until `locator.waitFor({state:'visible'})` resolves for the destination's `h1`
  (bell/KPI → `/events`) or `[data-testid="event-detail"]` (tray/toast → `/events/:id`, the drawer). Capped at 30 s
  (minus whatever the URL wait already used), not asserted — Playwright's own wait is timeout-bounded even if the
  page's main thread never answers (confirmed in task-22.9 investigation 1 and again here).
- **longtasks / longTaskMs**: `PerformanceObserver({entryTypes:['longtask']})` entries accumulated between the same
  two points (best-effort `page.evaluate`, raced against 3 s so a still-stalled page cannot hang the harness).
- **stateAtClick**: the quality badge's `data-state`, read right before the click (cheap, synchronous, before any
  stall begins) — not used to gate anything, just to confirm which condition a rep actually landed in.
- Nothing above is asserted on. The one real assertion is that every rep produced a row (`rows.length` equals the
  planned matrix size) — a broken harness fails loudly; a slow or hung navigation does not.

## 6. Conclusion

**Confirmed, not merely plausible.** The A/B isolates the one variable the brief named (`useTransitions`) and holds
everything else fixed (same build pipeline, same simulator speed/scenario per cell, same fps override policy, same
entry points, same click code). The result is not "a bit faster" — it is two to three orders of magnitude, in every
one of 12 cells, while the thing that should be unrelated to a React scheduling flag (how much long-task time the
scene/simulator burns) stays flat. That combination — one lever, uniform large effect on the dependent variable,
zero effect on the control variable — is what "confirmed" looks like for a scheduling hypothesis; it rules out "the
fix just happened to also reduce load" as an alternative explanation.

**Mechanism, now with direct evidence instead of inference:** `React.startTransition` lets React keep rendering the
*previous* commit (and, per the react-router docs read in section 3, avoid showing a Suspense fallback) until the
*new* tree is ready to commit without inconsistency. On this busy render loop, "ready to commit" apparently keeps
losing the race to whatever synchronous work is already queued (R3F's frame loop is driven by `requestAnimationFrame`,
outside React's scheduler; `liveStore`'s `useSyncExternalStore`-based 4 Hz flushes are forced-synchronous updates by
React's own design, exactly the case react-router's docs name as transition-unfriendly) — so the transition's render
is restarted or deferred for as long as that competing work keeps arriving, which on this sandbox is most of the
~17 s a navigation's own long tasks already take. `useTransitions={false}` makes the SAME click synchronous
(`setStateImpl` directly, no `startTransition`): React commits the new route on the next paint opportunity instead of
queuing behind a transition, and the heading appears in milliseconds — while the scene's own long tasks, which have
nothing to do with the router, keep running at their own unchanged pace in the background.

## 7. The four 22.9 "Open on a toast" symptoms, explained

`docs/progress/t22-9.md` section 5 recorded (not all in one run — across the session): (a) a 90 s hang after the
click, with the URL already correct; (b) a 5 s "element not found" with a DOM snapshot still showing `/live`'s own
content and the scene HUD reading "warmup"; (c) a 4th-run case where `live-toast` itself never appeared within 120 s;
and the general framing "four runs, four different symptoms, zero passes."

This investigation explains (a) and (b) directly and completely: they are the same mechanism at different points on
one continuous latency distribution, not two different bugs.
- **(a) the 90 s hang:** `median heading ms` in this session's own `toast` cells was 8205-21947 ms, but the
  distribution has real outliers — `toast/settled/3` in the baseline run took **70,948 ms total** (6 long tasks
  summing to 32 s) in a single rep, and task 21's own nav-latency table (`docs/progress/t21.md`) recorded a max of
  36,363 ms under similar load. A 90 s assertion timeout is generous but not infinite; under worse main-thread
  contention than this session happened to hit, the same unbounded-tail distribution plausibly produces a wait past
  90 s. This is consistent, not merely possible: every `toast` cell's `max` in section 5 is 3-4x its `median`.
- **(b) the 5 s "stuck on /live" snapshot:** this is exactly what `url ms ≈ 0` and `heading ms` in the thousands
  means, observed from a different vantage point. The URL already changed (confirmed, both investigations); a
  *different* assertion with its own 5 s timeout (not the one waiting on `event-detail`) sampled the page in the
  middle of that gap and saw `/live`'s DOM, because the committed tree had not yet swapped. "Scene still in warmup"
  in that snapshot is simply because the click happened inside the `warmup` condition — which this session's own
  `warmup` cells confirm is real and reproducible (`stateAtClick=warmup` on every non-`toast` rep).
- **(c) no toast within 120 s:** this session's own harness reproduced the *same category* of failure independently —
  `toast/burst` timed out waiting for `getByTestId('live-toast')` in 2 of 5 reps (baseline) and 1 of 5 (no-transitions)
  at 60 s, in both variants, i.e. regardless of the router-transition fix. That is direct evidence this symptom is
  **not** the navigation bug at all: it is the simulator's event-arrival timing under this sandbox's load, which the
  fix (a router-scheduling change) cannot and does not affect. `docs/progress/t22-9.md` itself reached the same
  conclusion by a different route ("the risk is in the speed of rendering... not in behaviour").
- **The fourth distinct "way"** (the session's phrasing: "a group count..." failing a third way, "Open on a toast"
  failing "a fourth way") is not independently reproduced here with the same label, and the 22.9 log does not give a
  clean fourth bucket distinct from (a)/(b)/(c) above — the most defensible reading of the evidence actually gathered
  (both there and here) is that (a) and (b) are two *symptoms* of one *unbounded, highly variable* latency
  distribution (the same root cause this session measured directly), while (c) is a second, independent, and
  unrelated timing issue in event arrival. Reported as an assumption, not invented as certainty: this document does
  not claim to have reproduced a fourth distinct mechanism.

## 9. Recommended fix and trade-offs

**Patch (not applied; `git diff -- src` is empty as of this report):**
```diff
--- a/src/app/App.tsx
+++ b/src/app/App.tsx
@@ -8,7 +8,7 @@
     <DataSourceProvider>
       <UiPreferenceSync />
-      <BrowserRouter>
+      <BrowserRouter useTransitions={false}>
         <AppRoutes />
       </BrowserRouter>
       <DebugReadout />
```

One line, one shared `<BrowserRouter>` — there is no per-route or per-`Link` scope in react-router's declarative
mode, so this affects **every** navigation in the app (confirmed by reading `dom-export.d.ts`/the implementation in
section 3), not just the four entry points measured. That is almost certainly desirable here (task 21 already found
the same multi-second hang leaving `/live` for `/trucks`, a fifth, unmeasured-by-this-session navigation that this
fix would equally speed up), but it is a global behaviour change and should be reviewed as one.

**Trade-offs:**
1. **Suspense fallback on the three lazy routes** (`/analytics`, `/events`, `/reports`; `src/app/routes.tsx`'s
   `guarded()` and the inline `<Suspense>` block) **has no `fallback` prop today**, so a suspended lazy import
   renders nothing. Under the current transition-wrapped behaviour, React's transition semantics keep the *old* page
   on screen while a lazy chunk loads, masking that blank gap (this is literally one of the two reasons
   react-router's own docs give for the transition default — section 3). Under `useTransitions={false}`, a
   **synchronous** navigation into a route whose chunk is not yet loaded would suspend synchronously with no
   fallback, i.e. a blank flash, for however long the dynamic `import()` takes (a local LAN fetch of a few hundred
   KB; not measured here — section 8, "cold lazy-chunk load"). Every number in section 5 was measured chunk-warm and
   would not show this. **Recommendation: add a lightweight fallback (a skeleton or the existing page-loading
   convention) to the three lazy `<Suspense>` boundaries in `routes.tsx` in the same change that adds
   `useTransitions={false}`**, so the masked gap becomes a visible, intentional loading state instead of a blank one.
2. **Task 21's GPU-release/nav-leak gate** (`src/scene/useReleaseOnUnmount.ts`, `e2e/t21-nav-leak.spec.ts`) disposes
   GPU resources "one task later" after a real unmount (`docs/progress/t21.md`), keyed off React's normal commit/
   effect lifecycle, not off whether the commit was a transition. Nothing read in this session suggests
   `useTransitions={false}` changes that lifecycle's ordering; if anything, a synchronous, fast commit removes the
   multi-second window during which `t21-nav-leak.spec.ts` already had to raise its canvas-leave wait to a 120 s
   backstop (`docs/progress/t21.md`, "Nav latency and the canvas wait"). This is a plausible improvement, not a
   verified one — **re-run `e2e/t21-nav-leak.spec.ts` (both default and `T21_LONG=1`) after adopting the fix**, per
   the brief's own scope line excluding nav-leak runs from this session.
3. **No other interaction found.** `grep -rn "startTransition\|useTransition\b" src` has no hits outside
   react-router's own internals, so no other app code is relying on the transition-wrapped behaviour today.

**Before adopting:** `pnpm typecheck && pnpm lint && pnpm test && pnpm i18n:check && pnpm build` (not run against the
patched tree in this session — the brief requires `src/` to end clean), then the full e2e suite, not just the four
specs this investigation touched.
