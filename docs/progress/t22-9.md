## 5. e2e runs (work item 5)

### `e2e/t22a-events.spec.ts`
First full run (webServer cold-started, browser not kept in foreground per the brief's own warning about Windows
throttling background browser processes): **10 passed, 4 failed**, total 30.4 minutes for 14 tests (one test alone
showed "Test timeout of 90000ms exceeded" after a reported 23.8-minute wall time — a symptom of the host throttling
the backgrounded Chromium process, not the app).

Reran each of the 4 failures **alone** (fresh webServer each time):
| Test | Alone result | Verdict |
|---|---|---|
| "windows the table: the DOM never holds more than a screenful of rows" | pass (28.7s) | throttling artifact in the combined run (`net::ERR_ABORTED` on a `page.goto`, consistent with the host killing a background navigation) |
| "a group count on the page equals the KPI popover count" | pass (37.5s) alone; **failed again in a later full-file run** ("element(s) not found" for the group chip within 5 s) | timing-sensitive against live data, not a logic defect — see below |
| "a live warn event raises a toast ...; at most 3 at once" | pass (1.2m) alone; **failed again in a later full-file run** (counted 4, not ≤3) | assertion too strict against a CSS exit animation — fixed, see below |
| **"Open" on a toast opens the event in the Events page** | **fails every time (4/4 across every run: the first combined run, twice alone, and the second combined run)** | **real, reproducible defect — see below. Not fixed (out of scope).** |

**"a group count..." — not a logic defect.** Read `EventsFilterBar.tsx`: only the `other` group chip is ever
conditionally hidden (`g.id === 'other' && n === 0 && filters.group !== 'other'`); every other group, including the
one that failed to resolve (`safety`), is always rendered once the filter bar has mounted. So `getByTestId` not
finding it within the assertion's 5 s window is the events page still loading/rendering at that instant under heavy
live-data churn (75 open alerts and climbing from the peak scenario), not a hide-at-zero bug. Not changed.

**"at most 3 at once" — fixed, a too-strict assertion, not an app defect.** Read `notifyDecision.ts`: the pure model
(`history.active`, unit-tested in `notifyDecision.test.ts`, "max 3 and eviction") never exceeds `MAX_TOASTS = 3`;
`applyDecision`'s eviction removes the victim from that model in the same step a new toast is added. The DOM count can
still transiently read 4, because sonner animates a dismissed toast out rather than deleting its node immediately, so
a freshly-shown 4th toast can share the DOM with the one it is still evicting for the length of that exit animation.
This is the same class of issue already accepted elsewhere in this project for Radix/sonner animations under
CPU-rendered e2e (BACKLOG, Task 19: "Radix exit animations start seconds late under SwiftShader"). Fixed the
assertion in `e2e/t22a-events.spec.ts` to `expect.poll(...).toBeLessThanOrEqual(3)` (5 s) instead of asserting on a
single instant.

**"Open" on a toast — confirmed real, reproducible, NOT fixed (out of scope).** Evidence across two separate
investigations:
1. First (debug instrumentation, since reverted — the spec file is otherwise unchanged from the pre-session version):
   added temporary `console`/`pageerror` listeners and `page.url()` logging around the click. `navigate()` fires
   correctly and the URL becomes `/events/<ulid>` **immediately** after the click (`page.url()` is tracked by
   Playwright at the navigation level and does not need the page's JS thread to be responsive) and stays correct for
   at least 10 more seconds (checked every second). Despite that, `expect(page.getByTestId('event-detail')).toBeVisible()`
   never resolved and the test hit its 90 s timeout — that assertion, unlike reading `page.url()`, requires executing
   JavaScript in the page to query the DOM, so the page's main thread was not responding to *any* script execution for
   tens of seconds after the click.
2. Second (a later full-file run, no instrumentation): failed faster this time (5 s, "element(s) not found" rather
   than a 90 s hang) with a full accessibility-tree snapshot captured at the failure instant. That snapshot shows the
   page **still rendering `/live`'s own content** (the bay list, visit tracker, KPI chips, map controls including the
   new X-ray button, and the scene HUD text **"Tier low · warmup · - fps"**) with a *new* toast already in the
   notification region — i.e. the live simulator kept producing and showing toasts on `/live`, while the route never
   visibly swapped to `EventsPage`/`event-detail`, even though (per investigation 1) the URL itself does change.
3. Both snapshots point the same way: this test is the only one in the file that clicks "Open" on a toast
   **immediately** on the first toast appearing — while the scene is still in `warmup` (its own HUD says so) and the
   live simulator's peak burst is actively flooding in events. The other tests that also leave `/live` for `/events`
   in this file (`the bell footer links to /events`, `a tray alert row has "Open in Events"`, `the inspector event
   body has the actions`) all do extra UI interaction first (open the bell, switch tabs), which gives the scene time
   to finish its warmup before they navigate away, and all of those pass reliably, including in both full-file runs.
4. **Not fixed.** The events/notify code is demonstrably correct (the navigation itself works, proven twice). What's
   left is either the live scene failing to tear down / yield the main thread promptly while still warming up under
   burst load, or (investigation 2) the route not visibly swapping away from `/live` under that same load — either
   way this is `src/scene/**` / `src/app/LiveScene.tsx` territory, out of this session's scope, and consistent with
   an already-flagged risk (BACKLOG, Task 21, "click-to-page time leaving /live", measured there at 3.2–13.6 s under
   SwiftShader — well under what's observed here). Reported for the owner to route to a scene-performance task, not
   silently patched by loosening the test's timeout.

**Final full-file run** (after the one spec fix above, debug instrumentation removed): **12 passed, 2 failed**
(7.4 minutes). The toast-count fix held (that test now passes). The two remaining failures:
- "a group count on the page equals the KPI popover count": failed again (same `events-group-safety` "element(s) not
  found" within 5 s) — a third distinct outcome for the same test across runs (pass alone twice, fail twice in a
  full-file run), consistent with the "events page still rendering under heavy live-data load at that instant" read
  above, not a logic defect. Not fixed, no code or test change: the risk is in the *speed* of rendering under this
  specific CPU-rendered, heavily-loaded test environment, not in behaviour.
- "Open" on a toast: failed a **fourth** way this run — this time `page.getByTestId('live-toast').first()` never
  became visible within its own 120 s wait (the test's *first* assertion, before any click), i.e. no warn/critical
  toast appeared on `/live` at all in that window. Combined with the other three failure modes seen across this
  session (a 90 s hang after navigating, a stuck-on-`/live` DOM snapshot with the scene still in `warmup`, and now no
  toast within 120 s), this test is unreliable in this environment for reasons that sit in the live scene / simulator
  timing, not in the code this session is scoped to touch. **Confirmed, reproducible, out of scope — not fixed.**
  Four runs, four different symptoms, zero passes: this is reported as a blocking finding for the owner, not a flake
  to wait out.

**2. Detention column clipping (EN).** Root cause, confirmed by reading `sections.tsx`'s `TruckLogSection`: the
table sits inside a `<div className="overflow-x-auto">` with the table itself carrying Tailwind's `min-w-[720px]` —
both exist only for the on-screen narrow-viewport case (horizontal scroll instead of column squeeze). Print has no
scrollbar and does not paginate horizontally, so a `min-width` wider than the printable area (A4 width 210mm minus
12mm margins each side = 186mm ≈ 703 CSS px at 96 dpi) does not shrink to fit; instead, in auto table layout, the
browser lets the last column's content extend to wherever the 720px-wide table puts it, and whatever falls past the
~703px page edge is simply not rendered — a physical clip, not a CSS ellipsis (consistent with the architect's report
of "Detentior": the glyphs for "n" were rendered at an x-position past the printable width). BN was unaffected only
because its shorter column text ("ডিটেনশন") happened to end before reaching that edge inside the same oversized
720px table, not because the table itself was narrower.
Fixed in `reports-print.css` (no change to `sections.tsx`'s column widths or pill was needed): `.rp-sheet
.overflow-x-auto { overflow: visible !important; }` and `.rp-sheet table { min-width: 0 !important; }` under
`@media print`, so the truck-log table (and any other `overflow-x-auto`-wrapped table) sizes to the real printable
width instead of the screen-only 720px floor. Confirmed by direct visual inspection of the regenerated
`docs/screens/t22c-print-en-previous.png` and `t22c-print-en-a4.png` screenshots (read directly, not rasterised from
a PDF): the "Detention" header and the "Detention" pill both render in full in EN, with clear margin to the sheet's
right edge, in both the current (in-progress, 4-row) and previous (complete, 10-row) shift documents.
