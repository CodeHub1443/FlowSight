## 1. Summary

Applied the fix task 22.10 proved: `src/app/App.tsx`'s `<BrowserRouter>` now passes `useTransitions={false}`, so
navigation no longer runs inside `React.startTransition`. Because a synchronous navigation into an unloaded lazy
chunk suspends without the transition's fallback-masking, every lazy route in `src/app/routes.tsx` now has an
explicit `fallback` (`src/app/RouteFallback.tsx`, a new text-free skeleton). `e2e/t22-10-nav-latency.spec.ts` is now
opt-in (`NAV_LATENCY=1`), not part of the default suite. Full regression (typecheck, lint, format, i18n, unit tests,
build) passes; the entry chunk grew 419 bytes (930,351 → 930,770), comfortably under budget. A reduced browser
verification matches task 22.10's projected numbers for the four event-centre entry points (medians 6-330 ms, down
from 7-22 s). **One open, unexplained finding, reported rather than hidden:** `e2e/t21-nav-leak.spec.ts`'s own
canvas-leave-time measurement (a different navigation, a different target route, a different trigger mechanism) did
not improve — see section 10. The leak gate itself (counts, heap) is unaffected and still passes.

## 4. Item 2 — Suspense fallbacks

`src/app/RouteFallback.tsx`:
```tsx
function Bar({ className }: { className: string }) {
  return (
    <div aria-hidden className={`bg-muted rounded-lg motion-safe:animate-pulse ${className}`} />
  );
}

export function RouteFallback() {
  return (
    <div data-testid="route-fallback" className="flex flex-col gap-3 py-1">
      <Bar className="h-7 w-48" />
      <Bar className="h-32 w-full" />
      <Bar className="h-32 w-full" />
    </div>
  );
}
```
- **Reused, not invented, visual language**: `bg-muted rounded-lg motion-safe:animate-pulse` is the exact class set
  of the one skeleton primitive already in the app (`src/features/analytics/perf/shared/WidgetStates.tsx`'s
  `Skeleton`, documented in `docs/06-visual-language.md` §4: "skeletons only on first load"). Not imported directly
  — that module is itself inside the lazy analytics chunk, and importing it from `src/app/` (always in the entry)
  would pull the whole `perf/shared` module graph into the `/live` entry. A second, parallel copy of six lines of
  classes was the smaller cost.
- **Text-free by design**, per the brief's own preference: no bilingual strings to add or maintain, no `role="status"`/
  `aria-busy` label either (the brief allows this trade-off explicitly: "prefer a text-free skeleton").
  `aria-hidden` on every bar instead, matching the existing `Skeleton` primitive's own choice.
- **Respects both themes**: `bg-muted` is a token (`src/index.css`), not a literal colour, so it follows the
  existing light/dark theme switch with no extra work.
- **Respects `prefers-reduced-motion`**: `motion-safe:` is a Tailwind variant that only applies inside
  `@media (prefers-reduced-motion: no-preference)`; under reduced motion the bars render static, filled blocks with
  no pulse.
- **Keeps the shell visible**: the fallback sits inside `PageLayout`'s content `<div>` (`src/app/AppShell.tsx`),
  itself inside `<main>` under `AppShell`'s `<TopBar>`. Neither `AppShell` nor `PageLayout` is inside any
  `<Suspense>` boundary, so the top bar and (for ordinary pages) the "Developed by TDI" footer stay mounted and
  visible underneath — unaffected by this change, since routes.tsx's structure already put the `Suspense` boundary
  only around the page content, not around the shell.
- **`/live` is untouched and does not get a fallback**: it is not lazy (`LivePage`/`LiveScene` are imported
  eagerly at the top of `routes.tsx`, `<Route path="live" element={<LivePage scene={<LiveScene />} />} />`, no
  `Suspense` wrapping it at the route level), so it cannot flash a fallback on any visit. `LiveScene.tsx`'s own
  internal, separate `lazy(() => import('@/scene'))` for `SceneRoot` has its own existing Suspense handling inside
  the scene feature; out of this session's scope (`src/scene/**` and `LiveScene.tsx` are not in the brief's file
  list) and not touched.
- **All four named routes, plus the dev-only one**: `/analytics/*`, `/events`, `/events/:id` (both routes share one
  `guarded()` call site, so one edit covers both), `/reports`, and `/dev/assets` (the `import.meta.env.DEV`-gated
  `AssetPreview` route — not named in the brief, but it is "any other `React.lazy` route," so it got the same
  treatment for consistency with the new rule in `docs/02-architecture.md`).

## 6. Item 4 — tests

**"Navigating to a lazy route shows the fallback first and then the page":** `src/app/App.test.tsx`, one
`it.each` over `/analytics?range=week` → `analytics-page`, `/events` → `events-page`, `/reports` → `reports-page`.
Each case asserts `route-fallback` is present **synchronously**, right after `render()`, before any `await` — React
renders the Suspense fallback on the same pass that it suspends, before the dynamic `import()`'s promise can
resolve even for an already-import-cached module — then awaits the real page and asserts the fallback is gone.
`/events/:id` is covered by a separate, simpler test (`/events/:id resolves to the same guarded, lazy EventsPage`)
**without** asserting the transient fallback: `/events` and `/events/:id` share one `lazy()` wrapper
(`EventsPage` in `routes.tsx`), which resolves its import once per process and never suspends again afterward, so
whichever of the two routes runs first in the file is the only one that can ever observe the fallback — confirmed
empirically (the `/events/:id` case failed exactly this way when first written with the same assertion, right after
the `/events` case had already warmed the chunk; fixed by splitting it out). All new and existing `App.test.tsx`
cases pass (30/30), and the whole `src/app/` test directory passes together (97/97, section 8) — ruling out
chunk-cache leakage from other files in the same vitest worker.

**"Navigation from `/live` to `/events` commits immediately in a jsdom test where the previous route stays busy":**
**attempted, found impractical, not added — with direct evidence, not an assumption.** Two disposable probes (since
removed; not part of the diff) against a minimal `<BrowserRouter>`/`<Link>` harness, outside `src/`:
1. `fireEvent.click` (Testing Library, synchronously `act()`-wrapped): the destination text was present
   **immediately after the click, with no `await`, in both the default (transition-wrapped) and the
   `useTransitions={false}` variant.** RTL's `act()` flushes pending transitions synchronously when used this way,
   regardless of the prop — there is no way to observe the difference this way.
2. A raw `element.dispatchEvent(new MouseEvent(...))`, bypassing RTL's own `act()` wrapping: **neither** variant had
   committed by the time of a synchronous check right after dispatch (both still showed the pre-click content).
   Without `act()`, jsdom/React does not flush the update synchronously enough to observe a difference either —
   the opposite failure mode from (1).
Between an environment that over-flushes (masking the bug) and one that under-flushes (masking the fix), there is no
window in plain jsdom + Testing Library where the two behaviours are observably different for a simple click. The
actual mechanism the fix addresses — a `requestAnimationFrame`-driven render loop and `useSyncExternalStore`-forced
synchronous updates competing with a pending transition for several seconds — has no jsdom equivalent (no real
frame loop, no real main-thread contention) short of hand-rolling fake schedulers deep in React's internals, which
was judged not practical for this brief. The real behaviour is exercised instead by the browser-based checks in
section 8.

**"Existing `RouteGuard` and route tests still pass":** confirmed, section 8 (`src/app/` directory run, 97/97; full
`pnpm test`, section 8).

## 10. Risks, assumptions, and the one open finding

- **Unresolved: `e2e/t21-nav-leak.spec.ts`'s canvas-leave-time to `/trucks` did not improve, while this session's
  own harness shows the fix working on the same build.** Differences between the two measurements, none confirmed
  as the cause: `/trucks` is a **non-lazy** placeholder route (no `Suspense` involved at all, so this is not a
  fallback-related question); `t21-nav-leak` drives navigation via a raw `window.history.pushState()` plus a
  manually dispatched `PopStateEvent`, not a real click through `navigate()`/`<Link>`; and it measures the moment
  the **old** scene's canvas leaves the DOM (unmount-complete), not the moment the **new** page's content becomes
  visible (mount-complete) — this session's harness only ever measured the latter. Logged in `docs/BACKLOG.md`
  (task-22.11 section) as a named follow-up rather than resolved here, per the instruction to report rather than
  explain away an unexpected result.
- The `e2e/t22a-events.spec.ts` full-file counts in this session are noisy for reasons confirmed to be external
  (ordinary foreground Chrome usage on this machine, not leftover test processes) — reported with that evidence,
  not asserted as a regression or dismissed without checking.
- `T21_LONG=1` (the 50-cycle, authoritative heap-slope gate) was **not** run, per the brief's explicit scope
  ("default mode only").
- The jsdom "commits immediately" test (item 4) was investigated with two disposable probes and found genuinely
  impractical in this environment, not skipped for convenience — see section 6 for the actual probe results.
